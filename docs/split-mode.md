# Split-режим: relay и MTProxy на разных хостах

## Когда это нужно, а когда нет

Для одного VPS split-режим не даёт ничего, кроме лишней задержки и ещё одной движущейся части. Он имеет смысл, если:

- несколько фронтов с разными доменами и в разных сетях должны питать один MTProxy с одним AD_TAG и общей статистикой;
- фронт стоит в «чистой» юрисдикции и его дёшево заменить при блокировке, а MTProxy с хорошим выходом к дата-центрам Telegram трогать не хочется;
- MTProxy уже работает где-то ещё.

Разные публичные порты смысла не имеют: клиент ходит на `https://домен/`, порт в ссылке `t.me/webproxy` не передаётся, нестандартный порт только выделяет хост. Внутренние порты и так произвольные.

## Как это устроено

```
front-хост                                              backend-хост
Интернет ─:443─▶ Caddy ─▶ relay ─▶ 127.0.0.1:2398        MTProxy :2398 ─▶ Telegram DC
                                   systemd-socket-proxyd  ▲
                                   └────── туннель (NetBird wt0 / WireGuard wg0) ──┘
```

Relay апстрима намеренно умеет ходить только на loopback: проверка конфигурации требует loopback-адрес в поле `backend`, а его юнит закрыт `IPAddressDeny=any` с разрешением только localhost. Поэтому на front-хосте на `127.0.0.1:2398` слушает `systemd-socket-proxyd` штатной парой `tgwp-backend.socket` и `tgwp-backend.service` и переправляет соединения на адрес backend в туннеле. Relay ничего не замечает.

Локальный MTProxy на front-хосте собирается апстримом как обычно, затем останавливается и маскируется. Это плата за то, чтобы не переписывать `install.sh` апстрима и не патчить его файлы. Зато `tgwebproxy backend local` возвращает всё на один хост без пересборки.

На backend-хосте ставится только MTProxy теми же скриптами апстрима, плюс правила nftables: порт 2398 открыт исключительно с перечисленных адресов, порт статистики 8888 только с loopback. Правила записываются в файл, который применяет апстримный `tproxy-firewall.service`, так что зависимость `mtproxy.service` от него работает без изменений.

Участок между хостами несёт обфусцированный MTProto. Держите его внутри шифрованного туннеля.

## Порядок установки

**1. Туннель.** Оба хоста в одной NetBird-сети или WireGuard-паре. Скрипт сам находит интерфейс `wt0`, `wg0`, `nb0` или `tun0` и его IPv4.

**2. Front.** Обычная установка, на шаге 0 роль `front`, затем адрес backend в туннеле:

```bash
TGWP_ROLE=front TGWP_BACKEND=100.64.0.5:2398 \
bash <(wget -qO- https://raw.githubusercontent.com/DigneZzZ/tg-webproxy/main/tg-webproxy.sh)
```

Backend в этот момент может ещё не существовать: установка завершится, панель покажет `backend недоступен`, пока он не поднимется. В конце установщик печатает готовую команду для backend-хоста с секретами и IP этого фронта в туннеле. Позже её печатает `tgwebproxy link`.

**3. Backend.** На втором хосте:

```bash
TGWP_ROLE=backend TGWP_SECRETS='e0fe…8b 0123…ef' TGWP_ALLOW_FROM=100.64.0.7 \
bash <(wget -qO- https://raw.githubusercontent.com/DigneZzZ/tg-webproxy/main/tg-webproxy.sh)
```

`TGWP_SECRETS` — секреты фронта через пробел (при режиме `all` их четыре), `TGWP_ALLOW_FROM` — IP фронта в туннеле или подсеть туннеля через запятую. AD_TAG задаётся здесь, потому что MTProxy живёт здесь.

**4. Проверка.** На front: `tgwebproxy backend` показывает, отвечает ли backend через туннель. Панель фронта считает `readyz` относительно локального сокета, поэтому реальную доступность показывает строка `backend` в разделе НАСТРОЙКИ.

## Команды

На front:

| Команда | Действие |
|---|---|
| `tgwebproxy backend` | роль, адрес backend, доступность через туннель |
| `tgwebproxy backend set <ip[:port]>` | направить relay на другой backend или перевести single-хост в split |
| `tgwebproxy backend local` | вернуть MTProxy на этот хост |
| `tgwebproxy link` | ссылки и готовая команда для backend-хоста |

На backend:

| Команда | Действие |
|---|---|
| `tgwebproxy secrets set '<s1 s2>'` | обновить секреты после `tgwebproxy mode` на фронте |
| `tgwebproxy allow <ip/cidr,...>` | кому открыт порт MTProxy |
| `tgwebproxy adtag` | спонсорский канал |
| `tgwebproxy update` | обновить MTProxy (пересборка только при смене закреплённого апстримом коммита) |

Меню `tgwebproxy` на backend-хосте показывает свою панель: службы, соединения из туннеля, пользователей MTProxy, трафик по туннельному и внешнему интерфейсу.

## Что учесть

- Сменили тип подключения на фронте — обновите секреты на backend, иначе новые ссылки не подключатся: MTProxy должен знать каждый секрет.
- `readyz` фронта не отражает состояние backend: сокет принимает соединение всегда. Смотрите `tgwebproxy backend`.
- Несколько фронтов на один backend: у каждого свой домен, одинаковые секреты, все IP фронтов в `allow`.
- Ограничение SSH, гео-фильтры и прочая защита хостов не входят в задачу этой утилиты.
